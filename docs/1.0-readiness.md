# Tracelet 1.0 readiness gates

Last reviewed: 2026-10-24

Tracelet 1.0 should mean that application teams can depend on the public API,
delivery protocol and documented browser behavior without discovering basic
contract ambiguity in production. It does not need to mean that Tracelet ships
a hosted analytics backend, dashboard or every possible integration.

Current position: npm `0.3.0` is the stable published line and `0.4.0-dev.0` is
the contract-hardening development line. The core SDK is usable today for
controlled integrations, but the operational evidence required for a 1.0
compatibility promise does not yet exist.

## Gate 1 — finish the 0.4 contract baseline

The tracked source of truth is `0.4-release-readiness.md`. Before moving toward
1.0, Tracelet needs:

- a durable reference Collector sink with a database-level unique `eventId` and
  restart-safe duplicate test;
- long-offline, large-queue and repeated-reload soak tests;
- private/ephemeral-mode and third-party-cookie-disabled checks;
- a maintained first-party Collector path tested against representative
  privacy/ad-blocking behavior;
- a beta and RC that pass the exact full CI suite and a real integration.

The public declaration snapshot, EventBatch v1, terminal lifecycle, adapter
failure policy, browser engine inventory, privacy data inventory and threat
model are already present in the 0.4 worktree.

## Gate 2 — define a support window

Before 1.0, replace “currently tested engine” with stable minimum versions and
continuous tests for those floors. The policy must cover desktop Chrome/Edge,
Firefox and Safari, and state the separate status of mobile Safari, mobile
Chrome and embedded WebViews.

Also define:

- how long the latest and previous 1.x minors receive security fixes;
- the deprecation period before a public API or browser floor changes;
- how IndexedDB schema and queued EventBatch data migrate across upgrades;
- which Node versions are supported for the reference Collector and tooling.

## Gate 3 — production evidence

A proposed measurable bar for 1.0 is:

1. at least two independent real applications use the same RC for 30 days;
2. at least one integration exercises offline persistence, Consent withdrawal,
   retry/429 handling and a deployed durable Collector;
3. a recorded soak run processes at least 100,000 synthetic events across
   reloads without queue corruption or unbounded memory growth;
4. no open release-blocking correctness, privacy or security issue;
5. the RC public declarations remain unchanged for at least 14 days.

These numbers are release criteria, not marketing claims. Record anonymized
evidence and observed limitations without copying production event payloads.

## Gate 4 — release and supply-chain operations

- Reproducible package contents, size budgets and installed-tarball smoke tests
  must stay green on supported Node versions.
- npm trusted publishing/staged approval, provenance and post-publish registry
  verification must be exercised on every prerelease.
- The release procedure needs a rollback/yank policy, security advisory path,
  changelog, migration guide and exact Git tag-to-package verification.
- Dependency and GitHub Actions updates must remain reviewable and pinned where
  appropriate.

## Gate 5 — documentation and adoption safety

- Quickstart, API Reference and examples must be checked against declarations
  and the current stable package.
- React, Vue, Next.js, Vite, Webpack and Rollup consumers must install the exact
  packed RC and complete production builds.
- Documentation must include the data inventory, threat model, failure
  semantics, browser policy, EventBatch protocol, Collector deployment and
  0.x-to-1.0 migration path.
- A minimal troubleshooting decision tree should cover blocked networks, CSP,
  quota exhaustion, Consent, duplicate delivery and version mismatch.

## Not required for 1.0

- A hosted dashboard, data warehouse or vendor-specific backend.
- CommonJS, UMD or an unversioned CDN global without demonstrated demand.
- DOM click/text autocapture; low-intrusion collection remains a design goal.
- `Analytics.group()` until real use cases establish its semantics.
- Exactly-once or audit-grade delivery. Tracelet remains at-least-once with
  Collector-side idempotency and browser best-effort lifecycle delivery.

## Suggested milestone sequence

| Milestone | Outcome |
| --- | --- |
| `0.4` | Contracts, lifecycle, failure semantics, protocol and support claims become explicit. |
| `0.5` | Durable reference Collector and restart/soak conformance evidence. |
| `0.6` | Privacy-mode, mobile/browser-floor and blocking-environment evidence. |
| `0.9` | Feature/API freeze, production integrations and 1.0 migration rehearsal. |
| `1.0` | Compatibility/support promise backed by an unchanged RC and recorded release evidence. |

Version numbers after 0.4 are planning labels, not promises to bundle unrelated
features. A milestone can be skipped or combined when every gate is still met.
