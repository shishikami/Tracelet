# Tracelet 0.4 release readiness

Last reviewed: 2026-10-24

Tracelet 0.4 is the contract-hardening milestone between the proven 0.3 runtime
and the eventual 1.0 compatibility commitment. It should reduce ambiguity and
operational risk rather than expand automatic collection or add a hosted
analytics backend.

## Public API and lifecycle

- [x] Snapshot complete emitted TypeScript declarations in addition to runtime
  export names.
- [x] Normalize the generated package-version literal so ordinary releases do
  not create false-positive API changes.
- [x] Make `shutdown()` terminal and idempotent, including plugin
  setup/teardown behavior and post-shutdown event diagnostics.
- [x] Isolate plugin transform, observation and teardown exceptions with
  payload-free diagnostics; retain explicit `init()` rejection for setup errors.
- [x] Define how storage, codec and compression exceptions affect host
  application calls.
- [x] Resolve the protocol-level `group` event versus the absence of an
  `Analytics.group()` method without accidentally expanding the 1.0 API.
- [x] Add an API review note for every intentional declaration snapshot update.

## Protocol and delivery

- [x] Publish the EventBatch v1 request, acknowledgement, retry, idempotency and
  compatibility contract in [`protocol-v1.md`](./protocol-v1.md).
- [x] Reject unsupported protocol versions in the Collector starter.
- [x] Keep Fetch `keepalive` inside an explicit page-exit payload budget.
- [x] Add a durable reference Sink with a database-level `eventId` unique
  constraint and restart-safe duplicate test.
- [x] Add long-offline, large-queue and repeated-reload soak coverage.

## Compatibility, privacy and security

- [x] Replace the generic “modern browsers” statement with a versioned support
  policy tied to CI and documented capability fallbacks.
- [x] Exercise non-persistent/ephemeral browsing contexts and prove that
  cross-origin delivery has no third-party-cookie dependency.
- [x] Document the default data inventory and a concise SDK threat model.
- [x] Verify the maintained first-party collector path recovers a durable queue
  after a representative client-side blocker aborts a vendor endpoint.

## Package, examples and documentation

- [x] Update React, Vue and Next.js starters to the current stable SDK line.
- [x] Move the repository to `0.4.0-dev.0` generated version metadata.
- [x] Replace beta-era website-framework and README status text.
- [x] Generate or mechanically validate website API Reference content against
  the emitted declarations.
- [x] Add a `0.3.x` to `0.4.x` migration page before the first beta.

## Release operations

- [x] End the release workflow after npm staged publishing instead of waiting
  for an unbounded manual approval.
- [x] Keep public Registry installation and Collector delivery verification in
  the independent post-approval workflow.
- [x] Pass the complete CI suite on the exact `0.4.0-beta.1` commit
  ([CI run #57](https://github.com/shishikami/Tracelet/actions/runs/40075491978)).
- [x] Publish `0.4.0-beta.1` through npm staged publishing with the `beta`
  dist-tag ([publish run #7](https://github.com/shishikami/Tracelet/actions/runs/40080595090)).
- [x] Reinstall and verify `tracelet-browser@0.4.0-beta.1` from the public npm
  Registry ([verification run #3](https://github.com/shishikami/Tracelet/actions/runs/40082914704)).
- [ ] Run the beta in at least one real integration before creating an RC.
- [ ] Publish `0.4.0-rc.1`, freeze public declarations and close every remaining
  release-blocking item above.

Items about multiple long-running production adopters remain 1.0 gates. The
0.4 release must make those integrations safe and observable, but it must not
claim that the evidence already exists.
